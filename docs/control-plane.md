# Control plane — batch 01 development slice

The API is a real Fastify/PostgreSQL application. It accepts only `registry.refresh`; it does not execute arbitrary agent prompts, repository commands or untrusted tools. Production startup deliberately fails until OIDC, TLS, scoped credentials and deployment controls are implemented. No provider samples replace failures.

## Local setup

Prerequisites: Node 24, npm lockfile installation, Docker with Linux containers or a separately provisioned PostgreSQL/Temporal environment. `infra/compose.dev.yaml` binds PostgreSQL 5432 and Temporal 7233 to loopback. It uses an explicit development database administrator for Temporal auto-setup; use separate service roles and managed secrets for production. Docker image tags are pinned for repeatability; the compose stack itself requires an actual Docker smoke test before being relied on.

Set `SAND_POSTGRES_PASSWORD` and `SAND_RUNTIME_DB_PASSWORD` in the shell from a secure password generator, then run `docker compose -f infra/compose.dev.yaml up -d`. Never commit their values. The first-init script creates the `sand_runtime` non-owner role. Existing volumes are preserved; no destructive reset is part of setup.

Run `npm run migrate` with `DATABASE_URL` set to the **migrator** connection, `SAND_RUNTIME_DB_ROLE=sand_runtime`, `SAND_BOOTSTRAP_LOCAL=true`, and generated UUIDs in `SAND_TENANT_ID` and `SAND_PROJECT_ID`. This explicit development fixture inserts a real tenant and project; their rows survive restart. It does not insert runs, events, models, prices or successful outcomes. Migrations are versioned and SHA-256 checked under an advisory lock. Never modify a migration already applied; add a new version.

For `npm run api` and `npm run worker`, replace `DATABASE_URL` with the **sand_runtime** connection. Set `SAND_AUTH_MODE=local-development`, `SAND_API_TOKEN` to a generated secret of at least 32 characters, `SAND_TENANT_ID` to the bootstrapped tenant UUID and `SAND_ACTOR_ID` to a local developer UUID. Set `TEMPORAL_ADDRESS=127.0.0.1:7233` for the worker. Provider configuration is described in the provider module documentation. Keep the API token exclusively in desktop main/process configuration. The API listens only on `127.0.0.1:4310`; no CORS/browser origin is accepted. Main-only bearer authentication is development identity, not production organization authentication.

`GET /health/live` checks the process. `GET /health/ready` checks PostgreSQL, runtime role privileges and the bootstrapped tenant. It does not claim that the Temporal worker/provider is healthy. All `/v1` endpoints require bearer authentication. `/v1/openapi.json` is generated from the route schemas. API errors expose stable metadata codes and remediation, never database exceptions or authorization headers.

## Durable admission and replay

POST `/v1/runs` body `{projectId,kind:"registry.refresh"}` requires `Idempotency-Key` (8–128 printable non-space characters). Server-owned unified policy version `registry-v1` permits only public registry discovery in development. Policy deny/ask prevents run/outbox mutation; rejected decisions have a durable metadata audit. Approval issuance/persistence remains unavailable. An accepted transaction atomically writes run, event, audit chain entry, idempotency receipt and outbox row, then returns 202. Same actor/tenant/operation/key plus different arguments returns 409; retry returns the original accepted response. Run state should then be refreshed via GET/events.

The dispatcher uses workflow ID `sand/<tenant>/<run>`, lease-based outbox claims and duplicate-start reconciliation. Failed dispatch uses bounded exponential backoff with jitter; 20 attempts dead-letter the outbox entry. A schema field exists for operator recovery, but a production recovery UI/API and on-call runbook are not delivered yet. The root workflow module owns actual Temporal execution.

Cancellation records `cancellation_requested` and a separate cancel outbox entry. It does not report `cancelled` until worker reconciliation confirms it. Row locks fence successful completion and registry writes after cancellation. Activity event keys make repeated transitions/snapshot commits idempotent. A saved snapshot replay returns its committed results, preventing fresh retry observations from being mistaken for the persisted outcome.

WebSocket `/v1/runs/:id/stream?after=sequence` reauthenticates every connection. The client receives `{type:"batch",events,lastSequence,hasMore}` and sends `{type:"ack",sequence}`. Event IDs and per-run sequence are durable. Acknowledgements bound in-flight messages, are not a durability source, and are not stored across connections; clients reconnect using their last persisted consumed cursor. Consumers must deduplicate event ID/sequence and replay gaps. Delivery is at-least-once, not exactly-once. Heartbeats, a 64-event in-flight limit, 512 KB output buffer ceiling, 15-second acknowledgement timeout and 1,000-event backlog ceiling bound slow consumers. Backlog sends `snapshot_required` with a REST URL. Full history remains available in paginated REST replay; applying a current-state snapshot must not be represented as consuming all historical events. REST polling uses exactly the same persisted event table.

## Data and security boundary

All tenant data uses FORCE RLS, transaction-local tenant identity and composite tenant foreign keys. Startup rejects SUPERUSER, BYPASSRLS and ownership of any application table. The migrator owns tables; the runtime receives narrow explicit grants. This protects against application query mistakes, not a compromised database owner. A single development identity is fixed in server configuration and cannot be changed through request JSON.

Audit/event tables reject UPDATE/DELETE. The audit insert trigger verifies per-tenant sequence, previous hash and SHA-256 body digest while locking the chain head. `GET /v1/audit/verify` verifies the entire chain against its current head; export returns JSONL with `after` and `limit` (maximum 1,000). `X-SAND-Has-More` and `X-SAND-Next-Cursor` explicitly indicate continuation; clients must keep paging until no next cursor remains. Only metadata, hashes and policy version are in audit bodies, not raw arguments/results. The initial audit schema does not yet include every future task/tool/worker/cost provenance dimension. Head anchoring outside PostgreSQL, WORM, retention and streaming large export are production gates; an owner who rewrites both chain and head is outside this integrity guarantee. Verification currently materializes the entire tenant ledger and requires streaming verification before large production datasets. Export is bounded and paginated.

OpenTelemetry spans cover Store transactions and connection handling; counters cover sent/replayed events, connections and auth rejection. API logs contain route patterns, correlation IDs, duration and status only. The API entrypoint initializes the shared telemetry SDK; actual remote export requires an explicitly configured OTLP destination. Collector delivery has not been verified by the backend integration tests. There is no claim of operational SLO achievement.

## Verification and remaining gates

`tests/integration/control-plane.integration.test.ts` uses the actual PostgreSQL WASM engine PGlite only in tests, applies the real migrations and executes as a non-owner role. It covers RLS negative paths, composite foreign keys, transactional rollback on failed audit, admission idempotency, policy denial, audit append-only/forgery checks, cancellation fencing and live Fastify HTTP/WebSocket replay/reconnect/slow consumer behavior. PGlite's single session is serialized by the test helper; it does not prove multi-connection PostgreSQL lock behavior. The `TEST_DATABASE_URL` suite explicitly skips without a supplied network PostgreSQL runtime connection and pre-provisioned `TEST_TENANT_ID`/`TEST_ACTOR_ID`. `tests/integration/control-plane-native.integration.test.ts` additionally starts a native PostgreSQL 17 process over loopback with separate runtime/migrator roles. Its three tests passed: 16 concurrent admissions collapse into one run/outbox record, accepted state survives API restart, cross-tenant reads fail, and cancellation races preserve state/event invariants. The external staging database test remains skipped when its environment is absent. Cloud-provider and Temporal evidence belongs to their own suites; Docker stack, load, backup/restore, multi-region and production IAM remain separate gates.

Operating cost: local API and DB incur machine resources; cloud cost is unknown until region, service tiers, storage/retention and workload are selected. Registry discovery prices are not assumed to be zero. Displayed model prices come only from provider evidence with timestamps; missing prices remain unknown. This slice does not implement token reservations or cost-aware routing.
